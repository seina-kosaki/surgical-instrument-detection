# エージェント・VS Code設定の最適化仕様

## 目的

Copilotが生成するコードを、最初から過剰に整備して動作確認が遅れる状態から、まず動作を確かめ、その後に読みやすく整える流れへ変更する。仕様確認、実装、検証、コード整備の役割を分け、手戻りとトークン消費を抑える。

## 決定事項

- 開発時は、まず動作する最小構成を優先する。
- 動作確認後に、型アノテーション・docstring・必要なコメントを整備する。
- Pythonの実行時設定はYAMLを基本とし、設定項目の用途をコメントで説明する。ツールや依存関係の設定は `pyproject.toml` など対応する標準設定ファイルに置く。
- 仕様確認でAI開発かどうかを確認し、AI開発の場合はAI開発向けの学習・評価要件とSkillを適用する。
- アクセスキー等の秘密値は `.env` に置き、Git管理対象に含めない。AIによる読み取り・表示・削除・変更は禁止し、Hookで直接操作を補助的に検知する。
- AI関連のモデル・ライブラリ等を選定する際は、公式GitHubで提供元や仕様を確認する。目的に合うHugging Face上の利用可能な成果物がある場合は、Hugging Faceからの利用を優先する。
- 破壊的操作や秘密情報の流出につながる危険なコマンドはHookで拒否し、判断が必要な操作は実行前に確認を求める。
- `.github/` 配下のAgent・Instructions・Skills・Prompts等は、本仕様に基づいて構成する。
- 仕様確認と仕様書作成は別々のAgentが担当し、Copilotのagentツールで次の担当へ委任する。
- 複数プロジェクト間で共有する外部向け契約仕様書を、各プロジェクトの `docs/contracts/` に作成する。
- 外部向け契約仕様書には入出力とDBスキーマを必須で記載し、データの保存・更新と他サービスから読取可能になるタイミングも記載する。エラー仕様と互換性の項目は含めない。
- コード変更で外部から見える入出力またはDB契約が変わる場合、対応する契約仕様書も同じ変更内で更新する。
- 外部Agentの仕様書を確認するSkillを用意し、関連する契約書だけを読み、コード全体の確認によるトークン消費を抑える。
- UIを設計する際は、具体例や選択肢を示して希望をヒアリングする。
- 仕様書の配置先は `docs/agent-customization-spec.md` とする。
- VS Code設定は用途に応じてユーザースコープの `settings.json` と `.vscode/settings.json` を使い分ける。後述のエージェント制御4項目はユーザースコープに指定し、ワークスペース設定で重複・上書きしない。
- Agent・Instructions・Skill・Hook・VS Code設定など、人が読む説明文、指示、質問、通知、出力は日本語にする。Agent名や工程名も日本語にする。
- Copilotの応答、質問、作業結果の報告は日本語にする。ユーザーが別の言語を指定した場合は、その指定に従う。
- VS CodeやHookの設定キー、スキーマで必須の値、プログラミング言語の識別子、コマンド、API名など、機械連携や技術上必要な文字列は原文のまま使用する。必要に応じて日本語で意味を補足する。

## エージェントの作業フロー

### 実行環境

- このワークフローは **Copilot** 実行環境を使用し、カスタムエージェントに `target: github-copilot` を指定する。`target` はスキーマを指定するもので、セッション対象は切り替えない。VS Codeではセッション対象にCopilotを選択する。
- Copilotでは `handoffs` ボタンを利用できないため、定義に `handoffs` を含めず、agentツールによるサブエージェントの呼び出しを使用する。
- 「01 仕様確認エージェント」は仕様決めでフロントエンド要否をYes/Noで確定し、必要な場合だけTypeScriptフロントエンドAgentと `ui-design-interview` Skillを使用する。フロントエンド不要なら、これらを呼び出さず工程入力・委任文脈にも含めない。
- 「01 仕様確認エージェント」は関連するバックエンド/APIの要否と言語も確定し、対象スコープのAPI全体、各APIの用途、入出力・データ項目、必要なユーザー可視状態を仕様化する。外部プロジェクト間の契約は既存の `docs/contracts/` 方針に従う。
- 要件合意後、「01 仕様確認エージェント」が「02 仕様書作成エージェント」を呼び出す。メインの担当は切り替わらず、呼び出し先の結果を受け取って報告する。
- 各呼び出しには合意済み要件、受け入れ条件、未解決事項、関連パス、前工程の結果を必要に応じて渡す。会話全体が自動共有される前提にしない。
- サブエージェントは結果を返して停止し、次のサブエージェントを呼ばない。呼び出し元がユーザーの指示や確認を受けて次工程を呼び出す。
- 仕様書作成後は停止し、ユーザーの実装指示なしに実装Agentへ進まない。UIと未確定APIの連携がある場合はモック・画面確認、API詳細確定、ユーザー合意、バックエンド、実API接続・統合確認の順に進む。コード整備はユーザーの手動確認成功後に限る。
- 呼び出しが利用できない、または失敗した場合は明示し、委任の宣言だけで成功扱いにしない。

### 作業範囲と停止条件

- 1回の委任は1工程に限定する。実装と最小の対象テストを終えたら結果を返し、全体検証は別工程とする。
- 変更前に局所仮説と、それを反証できる安価な検証を定める。変更直後は対象の診断またはdiffで検証する。
- 同じ失敗に対する修正・再実行は最大2回とし、解消しない場合は残件を報告して停止する。ただし「05 Pythonコード整備エージェント」の静的チェックは既存どおり最大1回とする。
- 範囲外の既存エラーは今回の変更との原因関係と残件を報告し、追って修正しない。
- 作業の区切りで途中結果と未完了事項を返す。時間指定は途中報告の目安であり、強制timeoutではない。

### 選択画面の表示名と順序

- 名前順でも通常の工程順に並ぶよう、各定義の `name` に2桁の番号を付ける。ファイル名は変更しない。
- 表示名は「01 仕様確認エージェント」、「02 仕様書作成エージェント」、「03 Pythonバックエンド実装エージェント」、「04 TypeScriptフロントエンド開発エージェント」、「05 Pythonコード整備エージェント」、「90 デバッグエージェント（随時）」とする。デバッガーの既存定義は変更対象に含めない。
- 仕様決め後は条件分岐する。フロントエンド不要ならTypeScript AgentとUI Skillを使わない。UIが必要かつAPI連携がありAPI詳細未確定の場合は「01 → 02初期仕様 → ユーザー実装指示 → 04モック・画面確認 →（要件変更時は01で再合意）→ 02 API仕様確定 → ユーザー合意 → 03 Pythonバックエンド → 04 API接続・統合確認 → ユーザー手動確認 → 05 Pythonコード整備」とする。API確定済み、またはバックエンド不要のUIでは不要なモック工程を省略する。対象に含まれないバックエンド/フロントエンド工程は省略する。
- UIが不要でPythonバックエンド/APIが必要な場合は、仕様確定後に「01 → 02 → ユーザー実装指示 → 03 → ユーザー手動確認 → 05」とする。バックエンドが不要でUIが必要な場合は、仕様確定後にユーザー実装指示を待ち、必要なら04でUIを実装・確認する。対象外の工程は省略する。
- 「90 デバッグエージェント（随時）」は不具合やテスト失敗時に使用する。通常工程の続きとして毎回実行するものではない。
- agentツールによる呼び出しにも、番号を含む表示名を使用する。番号は選択時の目印であり、ユーザーの合意・実装指示・手動確認を省略して自動実行するものではない。

### 01 仕様確認エージェント

- 目的、入出力、制約、成功条件を確認する。
- 不明点は、具体例または選択肢を添えて質問する。
- フロントエンド要否を必ずYes/Noで確定する。必要な場合に限りTypeScriptフロントエンドAgentと `ui-design-interview` Skillを使用し、不要なら呼び出さず工程入力・委任文脈にも含めない。
- 関連するバックエンド/APIの要否と言語を確定する。APIが対象の場合は対象スコープ全体と各APIの用途、入出力・データ項目、必要なユーザー可視状態を整理する。外部プロジェクト間の契約は `docs/contracts/` の既存方針に従う。
- AI開発かどうかをYes/Noで確認し、AI開発の場合は学習・評価・推論の対象範囲、問題種別、学習フレームワークまたは既存APIを確認する。学習を含む場合はAI開発・学習仕様に沿って要件を合意する。
- UIとAPIの連携がありAPI詳細未確定なら、API概要を含む初期仕様を作成する。画面モック確認後に要件変更が必要と判明した場合は、仕様を再合意する。
- 実装前に仕様を整理し、ユーザーの合意を得る。
- 仕様が合意されたら、「02 仕様書作成エージェント」を呼び出し、結果と仕様書のパスを報告する。

### 02 仕様書作成エージェント

- 合意した仕様を `docs/` 以下のMarkdownにまとめる。
- フロントエンド要否、バックエンド/API要否と言語、入出力、処理の流れを記載する。APIが対象ならスコープ内の全APIの用途、入出力・データ項目、必要なユーザー可視状態を仕様化する。Pythonの場合は主要なクラスやディレクトリの責務を記載する。
- AI開発かどうかと対象範囲を記載する。学習を含む場合は設定・ログ・指標・可視化の要件、独自学習か既存API利用か、および未合意の具体値や環境依存事項を明記する。
- UIと未確定APIの連携では、初期仕様にAPI概要を記載し、モック画面確認の結果を反映する。必要な要件再合意の後にAPI詳細仕様を確定し、ユーザー合意を待つ。確定済みAPIやバックエンド不要のUIでは、不要なモック工程を要求しない。
- 実装方法の詳細は、必要な範囲に留める。
- 仕様書が作成されたら、パスと未解決事項を返して停止する。呼び出し元はユーザーの実装指示を待ち、UIと未確定APIの連携がある場合は先に「04 TypeScriptフロントエンド開発エージェント」へモック確認を委任する。それ以外は対象に応じて03または04へ進む。

### 03 Pythonバックエンド実装エージェント

- API詳細が確定しユーザー合意済みの仕様に沿って、Pythonバックエンド/APIだけを動作する最小構成で実装する。TypeScript GUIやモックは担当しない。
- この段階では動作を優先し、型アノテーション、docstring、Ruff/Mypy対応、動作に不要なコメント整備を必須にしない。
- 実装後、最小の対象自動テストを実行し、結果と未確認事項を返して停止する。全体検証は別工程で行う。
- 自動テストが失敗した場合は「03 Pythonバックエンド実装エージェント」へ戻して修正する。同じ失敗への修正・再実行は最大2回とし、解消できない場合は推測で成功扱いにせず、失敗内容と未解決事項を報告する。
- 自動テストが通ったら、結果を呼び出し元へ返す。バックエンド単体案件ではユーザーの手動確認方法を案内し、フルスタック案件では04のAPI統合を先に行うため、バックエンド単体の手動確認を統合前の必須ゲートにしない。
- バックエンド単体の手動確認、またはフルスタックの統合確認で問題が見つかった場合は「03 Pythonバックエンド実装エージェント」へ戻す。ユーザーの最終確認が成功するまではコード整備へ進まない。

### 04 TypeScriptフロントエンド開発エージェント

- フロントエンドが必要と合意された場合だけ呼び出す。UI要件が未合意なら仕様確認へ戻し、`ui-design-interview` Skillはフロントエンド要件の設計時に必要な場合だけ使用する。
- UIとAPIの連携がありAPI詳細未確定の場合は、バックエンド実装より先に、TypeScriptフロントエンド単体で動かせるモックを作成し、VS Codeブラウザーで操作・表示を確認する。結果と仕様変更点を呼び出し元へ返す。
- 要件変更が必要な場合は「01」で再合意し、「02」がAPI詳細を確定してユーザーが合意するまでバックエンド実装・実API接続に進まない。API確定済み、またはバックエンド不要のUIでは不要なモック工程を省略する。
- API確定後、必要なバックエンド/APIが実装され利用可能になってから実API接続と統合確認を行う。モック専用コード・設定・データは本番ビルド・実行経路に混入させない。
- 利用可能なブラウザーツールを確認し、利用不可ならブラウザー未検証と明示する。HTTPやビルド等をブラウザー確認の代わりにせず、所有するサーバープロセスのみ管理し、秘密情報を扱わない。
- サブエージェントは呼び出さず、結果を返して停止する。Pythonコード整備対象がある場合も、ユーザー自身の最終手動確認成功前に05へ進まない。

### 05 Pythonコード整備エージェント

- ユーザーの手動動作確認が成功した後に限り、Pythonコードの型アノテーション、docstring、必要なコメントを整備する。TypeScript GUIは対象外とする。
- Ruff / Mypy等の静的チェックは整備後にまとめて実行する。型・docstringの有無を確認するための専用pytestは作らない。
- 静的チェックの失敗に対する修正と再チェックは最大1回とする。型・docstringの欠落と実害のある問題を優先し、残件は報告して停止する。
- コード整備でロジックを変更した場合に限り、関連するテストを実行する。ロジックを変更していない場合は、動作テストを繰り返さず静的チェックで確認する。

## 複数プロジェクト間の契約仕様

- 外部プロジェクトのAgentがコードベース全体を読まずに連携できるよう、各プロジェクトの `docs/contracts/` に外部向け契約仕様書を置く。
- 契約仕様書には、提供側と利用側それぞれの入出力を記載する。たとえば撮影APIでは受け取るデータと返すデータ、推論APIでは読み取るデータと出力を明示する。
- SQLiteを介して連携する場合は、テーブル名、カラム名、データ型、必須性などのDBスキーマを必ず記載する。
- データの保存・更新が行われる時点と、他のAPIやプロジェクトから読み取り可能になる条件を記載する。例：SQLiteへの保存完了後に成功応答し、推論APIは保存済みデータを読み取る。
- この仕様書の標準項目には、エラー仕様と互換性の説明を含めない。
- コード変更で外部から見えるAPI入出力、SQLiteスキーマ、またはデータの保存・読取タイミングが変わる場合、関連する `docs/contracts/` のMarkdownを同じ変更内で更新する。
- 内部実装のみの変更で外部契約に影響しない場合、契約仕様書の更新は不要である。

## 外部Agent仕様確認Skill

- 外部プロジェクトの仕様書や契約書と、現在のプロジェクトが提供・利用する契約を照合するためのSkillを作成する。
- Skillは対象となる外部仕様書と関連する `docs/contracts/` のみを優先して読み、プロジェクト全体のコードを一律に走査しない。
- 外部仕様書は同一のVS Code multi-root workspace内にあるもの、またはユーザーが指定したパス・URLから参照する。
- 入出力、DBスキーマ、保存・更新・読取タイミングの一致・不一致と、連携上の影響を報告する。
- 仕様書だけでは判断できない点は不明として示し、必要な場合に限って関連コードを追加確認する。
- 対象の仕様書にアクセスできない場合は推測で補わず、ユーザーに仕様書またはアクセス方法を確認する。
- Skillは比較結果の報告を担当し、外部プロジェクトの仕様書を自動変更しない。

## Python設定と構成

- 依存関係と環境構築には `uv` を使用する。
- 実行時に変更する設定は `configs/` 以下のYAMLに置き、各項目の用途をコメントで説明する。秘密値は `.env` から読み込む。
- YAMLは設定の責務や変更頻度に応じて分けるが、設定項目が少ない場合は1ファイルにまとめ、分割を目的化しない。
- 起動時に必要な値やモードは設定ファイルから読み込む。実行のたびにCLI引数でモードやログ名を指定する設計にしない。
- 固定された起動方法から設定を読み込めるようにし、`run` / `review`等のサブコマンドや、毎回の `log_name` 指定を避ける。ユーザーが設定ファイルやコードを編集する運用は許容する。
- `argparse`、`click`、`typer` は使用しない。`main`等の関数が引数を受け取る場合、その値は設定から渡し、ユーザーに毎回コマンドライン入力を求めない。
- このPCのCUDA環境に必要な `pyproject.toml` の `[[tool.uv.index]]` と `[tool.uv.sources]` は維持し、PyTorch追加時も変更・削除しない。追加後は `uv sync` を実行する。
- Ruff、Mypy、pytestの設定と開発依存関係は `pyproject.toml` に集約し、`dev` グループの依存関係は `uv sync` で同期する。独立した `ruff.toml` / `mypy.toml` は作成しない。
- 依存パッケージは用途に応じたdependency groupを選び、`uv add` で追加する。
- 外部ライブラリは可能な限り提供元を確認できる公開パッケージやホイールを使い、GitHubリポジトリをcloneせずに利用する。適切な配布物がない場合は代替方法を示して確認する。
- 外部パッケージを利用するだけでは、このプロジェクトの `[build-system]` は不要とする。自分のプロジェクトをパッケージ化して配布する場合に検討する。
- アクセスキー等の秘密値や環境差分は `.env` で管理する。秘密値を含む `.env` 系ファイルはGit管理対象に含めない。
- `.env.example` は変数名とプレースホルダーのみを含むテンプレートとし、実際のアクセスキー等は記載しない。Hookによるアクセス禁止の対象外とする。
- Hookは対象パスやツール操作を判定し、`.env` の直接操作の禁止を補助する。秘密値そのものを読み込んだり、ログやメッセージへ出力したりしない。
- AIによる秘密値を含む `.env` 系ファイルの直接読み取り・表示・削除・上書き・編集を許可しない。対象パスの別表記やシェル経由の操作も保護対象として扱う。
- アプリケーションが実行時に `.env` から設定値を読み込むことは許可する。ただし、秘密値の画面表示、ログ出力、外部送信は禁止する。
- 固定値と運用設定を混在させず、責務に応じて設定ファイルを分ける。
- 初期構成は必要最小限とし、責務が増えた場合に分割する。
- デバッグ時は標準的なF5起動で実行できるようにし、プロジェクトごとの `launch.json` 作成を原則不要とする。
- 主要な処理段階とデバッグに必要な情報をログに記録し、ログ保存先は原則として設定から決め、実行ごとのログ名は自動生成する。テンプレートの共通ロガーは `docs/logger-spec.md` に従い、プロジェクト直下の `logs/` を使用する。秘密値や巨大なデータ本体はログに出さない。
- 入口から出口まで処理を追える構成にし、ユーザーがブレークポイント等で確認しやすくする。

## AI開発・学習仕様

### 仕様確認

- 「01 仕様確認エージェント」は、対象がAI開発かどうかをYes/Noで確認し、仕様書に判定結果を記載する。
- AI開発の場合は、学習・評価・推論のどれが対象か、問題種別（分類・回帰など）、利用する学習フレームワークまたは既存APIを確認する。該当しない項目は「対象外」とする。
- AI開発に該当しない場合は、本節のAI学習要件とAI開発Skillを適用しない。

### 学習設定と実行ログ

- 独自の学習処理を実装する場合はHydraを設定管理に使用し、学習に必要な設定をYAMLで管理する。設定項目には用途をコメントで記載する。
- 学習・評価などの実行ログは、`logs/{実行種別}/{YYYY-MM-DD}/log_{連番}` の形式で実行ごとに分ける。実行種別は `train`、`test` など処理内容を表す名前とし、連番は同じ実行種別・日付の中で重複しないように採番する。
- 学習と評価で得られるloss、accuracyなどの適用可能な指標を記録し、指標の推移をグラフ画像として保存する。指標データも画像とは別に保存し、既存API利用時はAPIが提供する形式を優先する。評価指標はタスクに応じて選び、存在しない指標を出力必須とはしない。
- 独自の学習処理では、Early Stoppingと学習率スケジューラを必須とする。監視指標、最小化・最大化の方向、patience等の具体値はタスクとデータに応じて設定し、仕様確認または実装前に合意する。
- 既存API（YOLO等）を使った学習では、提供元の公式GitHubと既存コードの設定方法・ログ形式・評価機能を優先する。APIが標準で提供する機能を重複実装せず、Hydraや共通出力形式との両立が難しい場合は制約と採用する方法を仕様に記載する。

### 評価結果の可視化

- 分類問題では混同行列を画像として保存する。
- 回帰問題では推論値と正解値を比較できるグラフ、および標準偏差などの統計量をまとめた表を画像として保存する。表に含める統計量はタスクに応じて仕様で定める。
- 保存するグラフと表は日本語を正しく表示できること。利用する描画環境で日本語フォントを設定し、文字化けがないことを確認する。利用可能なフォントがない場合は、必要な環境設定を明示し、文字化けした画像を正常な成果物として扱わない。
- 学習・評価のログ、指標データ、画像の保存場所と命名は、同じ実行の成果物を相互に特定できるようにする。

### AI開発Skill

- AI開発時に繰り返し適用する手順をまとめるSkillを `.github/skills/ai-development/SKILL.md` に用意する。
- SkillはAI開発と判定されたタスクの該当工程で使用し、仕様確認、Hydra設定、ログと指標の保存、問題種別に応じた評価可視化、日本語表示の確認、既存学習APIを使う場合の公式実装優先を案内する。学習を含まないタスクには学習固有の要件を適用しない。
- Skillは合意済み仕様を補助する手順であり、未合意の要件を決めたり、実装や依存追加を自動的に承認したりしない。
- Skillは用途のある専門ワークフローに限って追加する。Skillの数を増やすこと自体を目標とせず、数の少なさだけを理由に新規作成しない。

## ログと設定エラーの通知

- Pythonでは原則として `print` を使用せず、標準の `logging` によるloggerを使用する。
- 設定不備で例外を送出する場合は、例外だけで終了せず、見直す設定ファイル・設定キーまたは環境変数名、不備の理由、期待する形式や範囲、修正方法をloggerで示す。
- 例：`configs/runtime.yaml の camera.timeout_seconds は正の数が必要である。設定値を見直すこと。` のように、修正箇所と対処が分かるメッセージにする。
- 原因となる設定項目を特定できない場合は推測で断定せず、確認できた事実と見直す候補を示す。秘密値は実値を記録せず、設定キーや環境変数名だけを示す。
- 例外には原因と設定項目の情報を持たせ、ユーザーへ通知する境界で一度だけログに記録する。同じ例外を各階層の `raise` 前後で重複して記録せず、ログ出力後も失敗を成功扱いにしない。
- 通常ログは開始・完了などの主要段階と必要な警告・エラーに絞り、詳細は必要時だけ有効にする `DEBUG` レベルへ分ける。
- フレーム単位・レコード単位のループやリトライで同じ情報を大量出力しない。必要な場合は件数や結果の集約、出力間隔の制御を使い、異なる失敗原因を埋もれさせない。

## UI設計ヒアリングSkill

- UIが必要と仕様決めで確定した場合に限り、React + TypeScriptを前提とする。
- UIの目的、利用者、画面、主要操作、データ/API、表示状態を確認する。
- 質問には、たとえば「学習状況の一覧画面／アノテーション画面」のような具体例や選択肢を添える。
- 要件が固まる前に大規模な画面構成や実装へ進まない。
- AI学習、アノテーション、データ収集APIなどの用途に対応する。
- SkillはUIが必要なタスクで設計ヒアリングが必要な場合だけ読み込み、フロントエンド不要のタスクでは使用せず委任文脈にも含めない。

## `.github` と `.vscode` の整理方針

- `copilot-instructions.md` は全タスク共通の短い原則に絞り、詳細は適用対象を限定したInstructions、Agent、Skillに分ける。
- カスタマイズの説明・指示・質問・ユーザー向け通知・Agent名・handoff名は日本語にする。Copilotの応答と報告も原則日本語とし、ユーザーが別の言語を指定した場合はその指定を優先する。
- 設定スキーマやツール連携で必須となるキー・識別子・コマンド名は変更せず、必要に応じて説明を日本語で添える。
- 仕様確認・仕様書作成・実装・デバッグの担当範囲を明確にする。
- 既存の `.github/` 指示ファイルを維持し、本仕様に必要な最小限の変更を行う。削除や新しいSkill/Agentの追加は個別の明示的な合意なしに行わない。
- `.vscode/settings.json` は、Copilotの自動修正が意図せず作業を繰り返す設定になっていないか確認し、保存時の整形とエージェントによる修正を区別する。
- ユーザースコープのVS Code `settings.json` に `chat.agent.maxRequests = 10`、`github.copilot.chat.agent.autoFix = false`、`chat.subagents.allowInvocationsFromSubagents = false`、`chat.agent.thinking.collapsedTools = "off"` を指定する。ワークスペース設定に同じ項目を重複指定・上書きしない。
- これらの設定は単一推論時間を強制制限するものではない。SDK等の実行環境への適用は未確認とし、適用される前提にしない。
- thinking effortはモデルピッカーで低めに手動選択する。旧非推奨設定は追加しない。
- `.vscode` の設定は、個別の `launch.json` を毎回作らなくても標準的なF5起動ができる方針と整合させる。
- Ruff、Mypy、pytestの実行タイミングは、実装時の動作確認とユーザー確認後のコード整備という段階に合わせる。

## 公式情報とHugging Faceの選定

- AI関連のモデル・ライブラリ・成果物を選定または導入する場合に、公式GitHubリポジトリを確認し、提供元・対応状況・導入手順を確かめる。選定・導入と関係しない通常のタスクで毎回確認する必要はない。
- 目的に合う成果物がHugging Faceで利用可能な場合は、Hugging Faceからの利用を優先する。
- Hugging Face上の成果物についても、公式GitHubとの関連性や提供元を確認する。公式性を確認できない場合は、その旨を示して利用可否を確認する。
- ライセンス、互換性、アクセス権、実行環境などの制約で利用できない場合は、制約と代替案を説明する。

## Hooksによる安全制御

- `.github/hooks/` のHookを用いて、ツール実行前に`.env`へのアクセスと危険なコマンドを判定する。
- Copilot実行環境の `preToolUse` イベントと、その入力・出力形式に従う。
- `.env` に対する読み取り、内容表示、削除、上書き、編集を拒否する。パス表記の違いやシェル経由の操作も考慮する。
- 秘密値を含まない `.env.example` は保護対象から除外する。
- `.env.example` にはプレースホルダーのみを許可し、実際の秘密値を含めない。
- アプリケーションによる実行時の `.env` 読み込みは許可するが、秘密値の表示・ログ出力・外部送信を拒否する。
- Hookは秘密値を取得・表示せず、判定に必要なツール名、引数、対象パスなどのメタデータだけを扱う。
- コードファイルの削除は、対象ファイルを明示したユーザーの削除指示または承認がある場合のみ許可する。一般的な修正・リファクタリング依頼を、ファイル削除の承認として扱わない。
- この削除制御はシェルコマンドだけでなく、編集ツールやパッチによるファイル削除にも適用する。承認を確認できない場合は実行を保留し、対象と理由を示して確認を求める。
- 通常の修正に伴うコードの行単位の削除は許可し、ファイル削除とは区別する。
- `git push --force` / `-f` / `--force-with-lease`、`git reset --hard`、`git clean -fd`等の履歴・作業内容を破壊する強制操作は、ユーザー承認の有無にかかわらず拒否する。単に `--force` の文字列だけで判定せず、Gitのサブコマンドと引数の組み合わせで判定する。
- ファイル削除が承認されていても、`.env`の保護やGitの強制操作禁止など、別の拒否規則は解除しない。
- 次のような操作は、作業範囲に対する破壊的変更、認証情報の流出、セキュリティ保護の無効化につながる場合に拒否する。
  - 広範囲または再帰的なファイル削除・上書き
  - Git履歴や作業ツリーを不可逆に破壊する操作
  - `.env`や認証情報の外部送信・出力
  - 権限変更、保護機能の無効化、出所不明なスクリプトの無確認実行
- 明確に高リスクな操作は拒否し、危険性や影響範囲を引数だけで安全に判断できない場合は実行を保留してユーザー確認を求める。
- Hookが操作を解析できない場合や判定できない場合は、許可せずユーザー確認を求める。
- Hookは小さく監査可能に保ち、許可・拒否・確認の理由を明示する。誤検知によって通常の開発操作を妨げないようにする。
- HookはCopilotのツール実行を補助的に制御する仕組みであり、OS全体のアクセス制御ではない。解析できない操作やHookの無効化・タイムアウトを含め、すべての操作の検知・拒否は保証しない。
- `.env`の読み取り・編集・削除、秘密値の出力/送信、代表的な危険コマンドを拒否するテストを用意する。
- コードファイルの未承認削除を拒否し、明示承認済みの対象ファイル削除と通常編集での行削除を許可するケースも検証する。Gitの強制操作は承認があっても拒否することを検証する。

## 受け入れ条件

- 実装前に仕様確認と仕様書作成の段階がある。
- 全カスタムエージェントが `target: github-copilot` を指定し、未対応の `handoffs` 属性を含まない。
- 選択画面用の `name` と呼び出し名は「01 仕様確認エージェント」「02 仕様書作成エージェント」「03 Pythonバックエンド実装エージェント」「04 TypeScriptフロントエンド開発エージェント」「05 Pythonコード整備エージェント」「90 デバッグエージェント（随時）」に一致する。デバッガーの既存定義は変更しない。
- 要件合意後に「02 仕様書作成エージェント」を実際に呼び出し、結果と仕様書のパスを報告する。実装の開始とコード整備への移行は、それぞれユーザーの指示と手動確認成功を待つ。
- 仕様決めでフロントエンド要否が必ずYes/Noで確定され、不要な場合はTypeScript AgentとUI Skillを呼び出さず委任文脈にも含めない。バックエンド/APIの要否と言語、API全体像と用途・入出力・データ項目・ユーザー可視状態も仕様化される。
- UIが必要かつAPI連携・API詳細未確定の場合、ユーザーの実装指示後、バックエンド実装前に04が単体動作するモックを作り、VS Codeブラウザーで画面を確認する。結果を仕様へ戻し、必要な要件再合意、API詳細確定、ユーザー合意後に03へ進む。確定済みAPIまたはバックエンド不要のUIでは不要なモック工程を省略する。
- 03はPythonバックエンドと最小対象テスト、04はTypeScriptモックと必要時の実API接続・ブラウザー確認、05はPythonコード整備に責務を限定する。手動確認成功後のみ05へ進み、最小実装・対象テスト・試行上限を維持する。
- 「04 TypeScriptフロントエンド開発エージェント」は利用可能なブラウザーツールを確認し、利用不可ならブラウザー未検証と明示する。HTTPやビルド等をブラウザー確認の代わりにせず、所有するサーバープロセスのみ管理し、秘密情報を扱わない。
- ブラウザーツールの設定は公式互換性の確認後に親側で選定し、MCP導入・外部データ送信には事前承認を必要とする。結果報告ではブラウザー確認とF5手動デバッグを区別する。
- 「04 TypeScriptフロントエンド開発エージェント」による確認はユーザーの手動確認や、ファイル削除等に必要な明示承認を代替しない。既存のF5デバッグ例は利用可能なまま維持する。
- 動作確認より前に、全コードのdocstring・コメント整備を強制しない。
- フルスタック案件では03の対象自動テスト後に04がAPI統合を行い、その後にユーザーが最終手動確認を行う。バックエンド単体案件では03の対象自動テスト後にユーザーが手動確認する。Pythonコード整備対象がある場合のみ、確認成功後に05へ進む。TypeScriptのみの案件では05を呼び出さない。
- 静的チェックの修正・再チェックは最大1回で停止し、ロジック変更時だけ関連テストを実行する。
- エージェント制御4項目が指定値でユーザースコープに設定され、ワークスペースで重複・上書きされない。単一推論時間の強制制限やSDK等への適用を保証せず、thinking effortはモデルピッカーで低めに手動選択し、旧非推奨設定を追加しない。
- 1委任1工程とし、実装と最小対象テストの後に結果を返す。全体検証は別工程とし、仕様合意・実装指示・ユーザー手動確認後のみ05へ進む既存ゲートを保持する。
- 変更前の局所仮説と安価な検証、変更直後の対象診断またはdiffによる検証を行う。同じ失敗の修正・再実行は最大2回（コード整備の静的チェックは最大1回）とし、範囲外既存エラーは原因関係と残件を報告して追わない。区切りで途中結果を返し、時間指定を強制timeoutとして扱わない。
- YAMLの各設定に、何を設定する項目かコメントを記載できる。
- YAMLの分割は責務・変更頻度で判断し、設定が少ない場合は分割しない。
- 実行設定はconfigから読み込み、毎回のモードやログ名のCLI指定を要求しない。
- PyTorch導入時はpyproject.tomlにuvのindex/sourceを設定してから `uv sync` する。
- 標準的なF5起動を可能にし、プロジェクト固有の `launch.json` 作成を原則不要とする。ログ名は自動生成し、秘密値はログに出さない。
- Pythonの通常出力は `print` ではなくloggerを使用する。
- 設定不備による例外では、見直す設定ファイル・項目名と理由・対処方法をログから特定でき、秘密値の実値は記録しない。
- 同一例外の重複記録やループ内の大量ログを避け、通常ログと必要時の `DEBUG` ログを分ける。
- AI関連の選定で公式GitHubを確認し、利用可能な場合はHugging Faceを優先する。
- `.env`への代表的な直接読み取り・表示・削除・変更をHookが検知して拒否する。
- `.env.example` は秘密値を含まないテンプレートとして保護対象から除外する。
- 破壊的または秘密情報の流出につながるコマンドをHookで拒否し、曖昧な場合は実行前に確認する。
- コードファイル削除は対象を明示したユーザー指示または承認を必須とし、シェル・編集ツールの両方を対象とする。通常編集での行削除は許可する。
- Gitの履歴・作業内容を破壊する強制操作は、ユーザー承認があっても拒否する。
- 公式GitHubの確認はAI関連のモデル・ライブラリ等の選定・導入時に行い、通常タスクへ一律に要求しない。
- 仕様確認時にAI開発かどうかが明示され、AI開発の場合だけAI学習要件とAI開発Skillが適用される。
- 独自学習ではHydra設定、実行種別・日付・重複しない連番によるログ分離、適用可能な指標の記録とグラフ化、Early Stoppingと学習率スケジューラが仕様化される。
- 分類では混同行列、回帰では推論値と正解値の比較グラフおよび標準偏差などの統計表が画像で保存され、日本語の文字化けがない。
- YOLO等の既存学習APIを使う場合は公式実装と既存コードの流儀を優先し、重複する独自機能を追加しない。
- AI開発SkillはAI開発でのみ使う専門手順として定義され、Skillの数自体を目標にしない。
- `.github/` のAgent・Instructions・Skills等が本仕様に沿って配置されている。
- 仕様確認Agentから仕様書作成Agentへ引き継ぎ、ユーザーの実装指示後に合意済みフロントエンド/APIスコープに応じた工程へ分岐し、ユーザー手動確認成功後に限りPythonコード整備Agentへ進む。
- 外部向け契約仕様書を各プロジェクトの `docs/contracts/` に置き、入出力・DBスキーマ・保存/読取タイミングを記載する。
